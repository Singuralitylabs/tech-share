# AI駆動開発の流れとClaude Codeの基本操作 プレゼン骨子（ハンズオン・約55〜60分）

> **狙い**：AIと本格的に開発を進める道具「Claude Code」に実際に触れてもらい、**「やりたいことを伝える → AIが作る → 結果を見て次の指示を出す」というリズム**を体で覚えて帰ってもらう。
> **通しのメッセージ**：AI駆動開発は「魔法の呪文」を覚えるゲームではない。**小さく回すループ**と、**作る前に計画を挟む**こと。この2つだけで成果物の質は変わる。
> **形式**：ハンズオン（参加者が各自の環境で手を動かす）。座学とハンズオンを交互に挟む「説明5分 → 手を動かす10分」のサンドイッチ構成。
> **対象**：エンジニア〜非エンジニア混在。**ターミナルを触ったことがない人がいる前提**で組む。
> **各パートの型**：座学パートは「概念 → 図 → 一言のたとえ」、ハンズオンパートは「**画面に出しっぱなしにする手順スライド**（コピペできる指示文つき）」で統一する。
> **絶対に守ること**：ハンズオンで**誰も置いていかない**。手が止まった人は、追いつかせようとせず**「見るだけモード」に切り替えてもらう**。「見ているだけでもOK」を冒頭で明言し、手順は全部資料に残すと約束しておく。

## 前提となる設計判断（なぜこの構成か）

| 判断 | 理由 |
|---|---|
| 題材を **1枚のHTMLページ** にする | ブラウザで開けば結果が見える＝**「確認」のステップが非エンジニアでも成立する**。Node.js のセットアップ・npm・ビルドが要らず、環境差で詰まらない。 |
| Git を必須にしない | 混在層で最初のハードルになる。`/init` の説明では触れるが、ハンズオンの必須手順から外す。 |
| **ターミナル操作を最小限にする** | フォルダ作成・移動・ファイルを開く操作は、**GUI（Finder / エクスプローラー）でできる道を必ず併記**する。ターミナルで打つのは実質 `claude` の1回だけにする。**OS差でコマンドが割れる箇所を、そもそも通らないようにする**狙いも兼ねる。→ 詳細は「付録：OS別コマンド対応表・GUIでのやり方」 |
| **Windows は PowerShell / Windows Terminal に統一** | `cmd.exe`（黒い画面のコマンドプロンプト）は `~` もスラッシュ区切りも使えず、手順が3系統に増える。案内の段階で PowerShell に寄せる。 |
| ハンズオンを2回に分ける | 1回目は「ループの体感」、2回目は「計画を挟むと何が変わるか」。**同じ題材の続き**にして、差分として体験させる。 |
| **ペア作業を採用しない** | 混在層では「教える側」に負担が寄り、両方の手が止まる。詰まった人は**見るだけモードへ切り替え**、ハンズオン①の完成物を配布して**②から復帰できる導線**を用意する方を選ぶ。 |
| コマンドの紹介を後半に置く | 先にコマンド一覧を見せると暗記モードになる。**困った体験をしてから**「それを解決するのがこのコマンド」と出す。 |

## 2. そもそも Claude Code とは／なぜ今なのか（4分）

**話すポイント**

**① Claude Code とは何か（1分半）**
- ひとことで言うと、**ターミナルの中で動くAIの開発パートナー**。
- ChatGPT のようなチャットとの決定的な違いは、**自分のPCのファイルを直接読んで・書いて・コマンドまで実行する**こと。
  - チャットAI：人が状況を説明する → コードをもらう → **人がコピペして戻す**
  - Claude Code：**AIが自分でファイルを見に行き、自分で書き換える**。人は指示と確認だけ
- つまり「**質問に答えてくれるAI**」ではなく「**作業をするAI**」。ここが今日の全体の前提。
- 勝手に何でもされるわけではない。**ファイルを変更する前に必ず許可を聞いてくる**（後のハンズオンで実物を見せる）。

**② なぜ今、これが来ているのか（2分半）**
- 3つだけ挙げる。細かい技術の話はしない。
  1. **AIが「長い作業」を最後までやり切れるようになった**
     昨年までのAIコーディングは「書いている途中を予測して補完する」が中心。今は「**このタスクを丸ごとお願い**」が成立するようになった。一問一答から、複数ステップの作業へ。
  2. **コピペの往復が消えた**
     AIが自分でプロジェクトを読みに行けるので、**人間が毎回状況を説明する必要がなくなった**。ここが体感の差として一番大きい。
  3. **「任せる」と「暴走しない」が両立した**
     ファイルを触る前の許可確認、作る前に計画を出させる仕組み（＝今日のパート6）が整った。だから**安心して任せられる**ようになった。
- 前回のトレンド講座で触れた「**道具 → 自分で回り続ける相棒**」への変化。その**実物がこれ**、という位置づけで繋ぐ。

**見せるもの（1つ）**
- 「聞く」vs「作る」の2列対比表（`ba` クラスで実装）。**「人がコピペして戻す」→「人は指示と確認だけ」** の対比が要点。
- ※ 将来的には**図版**（左＝チャットにコードを貼ってコピペで戻す絵／右＝Claude Code がファイルを直接編集している絵）に差し替えると、「**コピペの矢印が消える**」がより速く伝わる。

**掴みに使えるネタ（任意）**
- 「**今見てもらっているこのスライド自体、Claude Code で作っています**」。開発以外にも効く道具だと一言で伝わり、非エンジニア層の関心が繋がる。

**スライド見出し（重要な設計判断）**
- 1枚目の見出しは **「Claude Code とは ―「作業をする」AI」**。**見出しで「何であるか」を言い切る**。
- 当初は「AIに"聞く"から、AIと"作る"へ」を見出しにしていたが、それだと**「Claude Code とは何か」の答えがデッキを探しても見つからない**（定義が比較表の下の箇条書きに埋もれる）。**定義は表より上に1行で先出しする**。
- タグライン **「AIに"聞く"から、AIと"作る"へ」** は、見出しの下の本文1行目に置く。

**補足メモ**：**歴史や技術背景に深入りしない**。混在層向けなので **3枚・計4分**（1枚80秒）で切り上げる。エンジニアから細かい質問が出たらクロージング後のQ&Aに回す。

## 3. AI駆動開発の基本ループ（指示→生成→確認→改善）（5分）

**話すポイント**
- AI駆動開発は、**4つのステップをぐるぐる回すだけ**。
  1. **指示する**：やりたいことを言葉で伝える
  2. **AIが作る**：Claude Code がファイルを作る・直す
  3. **確認する**：**自分の目で結果を見る**（ここが一番大事）
  4. **次の指示を出す**：良かった点はそのまま、直したい点だけを伝える
- 一番よくある失敗は **③をサボること**。AIの「できました」を鵜呑みにして次に進むと、ズレが積み上がる。
- **1周は小さく**。「全部作って」より「まず表示だけ作って」の方が結果的に速い。ズレたときに戻る距離が短いから。
- 指示のコツは3つだけ：
  - **やりたいこと**を書く（作り方ではなく）
  - **どうなったら完成か**を書く（「ブラウザで開いて一覧が見えたらOK」）
  - **ダメだった点だけ**を次に伝える（毎回ゼロから説明し直さない）

**見せるもの（1つ）**
- 4ステップの円環図。**③「確認」だけ色を変えて強調**する。

**ひとことスライド文言案**
> 「小さく回す。毎回、自分の目で見る」

**補足メモ**：非エンジニアにも刺さるパート。「これは開発の話じゃなくて**仕事の進め方の話**です」と一言添えると混在層がついてくる。

## 4. 【ハンズオン①】ループを1周まわす（10分）

**題材**：ブラウザで開ける「今日のふりかえりメモ」ページを1枚つくる。

**手順**

### STEP 1：作業フォルダを用意して、そこでターミナルを開く（スライド1枚目・最初の2分だけ表示）

> ここだけ Windows / Mac で操作が違う。**AとBはどちらでも同じ結果**なので、好きな方を選んでよいと伝える。

**ルートA：マウスでやる（ターミナルが苦手な人はこちら・推奨）**

| | Windows | Mac |
|---|---|---|
| ① フォルダを作る | デスクトップで右クリック →「新規作成」→「フォルダー」→ **`techshare-demo`** と名前をつける | デスクトップで右クリック →「新規フォルダ」→ **`techshare-demo`** と名前をつける |
| ② そのフォルダでターミナルを開く | フォルダをダブルクリックで開き、**上のアドレスバーに `powershell` と入力して Enter**<br>（Windows 11 なら、フォルダを右クリック →「**ターミナルで開く**」でも可） | 「ターミナル」を起動し、**`cd ` と入力（最後に半角スペース）** → **フォルダをターミナルの窓にドラッグ&ドロップ** → Enter |

**ルートB：コマンドでやる（ターミナルに慣れている人はこちら）**

Mac（ターミナル）
```
mkdir ~/Desktop/techshare-demo
cd ~/Desktop/techshare-demo
```

Windows（PowerShell）
```
mkdir ~\Desktop\techshare-demo
cd ~\Desktop\techshare-demo
```

### STEP 2〜：ここからは Windows / Mac 共通（スライド2枚目・出しっぱなし）

1. **Claude Code を起動する**
   ```
   claude
   ```
2. **1回目の指示**（そのままコピペ）
   > 今日のふりかえりを書き留める1枚のHTMLページを作ってください。
   > 「やったこと」「気づいたこと」「明日やること」の3つの入力欄と、一覧表示があるシンプルな見た目にしてください。
   > ファイルは index.html の1ファイルだけにして、ブラウザで開けば動くようにしてください。
3. **確認：自分の目で見る**
   - **フォルダの中の `index.html` をダブルクリック**する ← **Windows / Mac 共通・これが一番確実**
   - （ターミナルから開きたい人向け：Mac は `open index.html`、Windows は `start index.html`）
4. **2回目の指示**（見た目の感想を、そのまま言葉で伝える）
   > 全体をもう少し見やすくしてください。文字が小さいので大きく、余白を広げてください。
5. **ブラウザを再読み込みして、もう一度確認**

**発表者が実演で見せること**
- 実行前に **Claude Code が「このファイルを作っていいですか」と確認してくる**こと。→ 許可を出すのは自分。**勝手に何かされるわけではない**と示すのが、初めての人の安心につながる（パート2で言ったことの実物）。
- 生成中の画面（何をしているかが流れる）を見せて、「**中で何が起きているか見えるのが Claude Code**」と伝える。

**ここで必ず言うこと**
- 「**指示は日本語でOK**です。かっこいい書き方は要りません」
- 「**気に入らなければ何度でも言い直せます**。それがループです」
- 「**追いつかなくても大丈夫**です。次のハンズオンは完成品を配るので、そこから合流できます」

**ひとことスライド文言案**
> 「まず1周。伝える → できる → 見る → 直す」

**補足メモ**：巡回して、詰まっている人の**画面の何行目で止まっているか**を拾う。よくある詰まり＝(a) フォルダ移動ができていない (b) 起動時のログインが未完了 (c) 許可プロンプトに気づかず待っている。**(c) が一番多い**ので、スライドに「許可を聞かれたら `y` / Enter」と明記しておく。

## 5. バイブコーディングの壁（4分）

**話すポイント**
- ここまでの進め方＝**「バイブコーディング」**（雰囲気で指示して、雰囲気で直す）。**小さいものを作るには最高に速い**。今日体験した通り。
- ただし、**規模が大きくなると崩れる**。
  - 指示が積み重なると、AIが**前に決めたことを忘れる**（正確には、毎回の指示だけを見て動くので、全体の方針が共有されていない）
  - 「直して」を繰り返すうちに、**直したはずの場所が元に戻る**
  - どこまで進んだのか、**人間の側も分からなくなる**
- 実演：**わざと大きすぎる指示を1つ投げてみせる**（例：「ログイン機能とデータ保存とグラフ表示を全部足して」）。返ってきた結果が想定とズレる、または一度に変更が多すぎて確認できない様子を見せる。
- 原因は AI が悪いのではなく、**「何を作るか」が決まらないまま作り始めているから**。人間同士でも同じ。

**見せるもの（1つ）**
- ビフォー/アフター表：
  | | いきなり作る | 計画してから作る |
  |---|---|---|
  | 小さい変更 | **速い** | やや冗長 |
  | 大きい変更 | 手戻りが増える | **手戻りが減る** |
  | 確認のしやすさ | 何が変わったか分からない | 事前に読んで判断できる |

**ひとことスライド文言案**
> 「雰囲気で作れる。でも、大きくなると崩れる」

**補足メモ**：バイブコーディングを**否定しない**。「小さいものには今でも最適」と明言した上で、「一歩進んだやり方」として次に繋ぐ。ここを否定から入ると、パート4で成功体験を得た人の熱が冷める。

## 6. 計画を立ててから作る（Plan → 実装 → 確認）（5分）

**話すポイント**
- Claude Code には、**作る前に「作業計画」を出させて、人間が読んでからOKを出す**進め方がある（プランモード）。
- 使い方はキー操作ひとつ：**`Shift + Tab` を2回押す**とプランモードに入る。（`Shift + Tab` は「通常 → 編集を自動承認 → プランモード」と切り替わる）
- プランモードのあいだ、Claude Code は**調べるだけで、ファイルを書き換えない**。代わりに「こう進めます」という計画を出す。
- 人間の仕事は**計画を読んで判断すること**の一点。

## 8. `/init` と、知っておくと便利な基本コマンド（7分）

**話すポイント**

**① まず `/init`（このパートの主役）**
- ハンズオンで「毎回、同じ前提を説明し直している」感覚があったはず。それを解決するのが `/init`。
- `/init` を実行すると、Claude Code が**プロジェクトの中身を自分で調べて `CLAUDE.md` というメモを作る**。
- `CLAUDE.md` は**次回以降、毎回自動で読み込まれる**。つまり「このプロジェクトはこういうものです」を**一度書けば、毎回説明しなくてよくなる**。
- **その場で実行してもらう**（1分）。作業フォルダで `/init` → 生成された `CLAUDE.md` を開いて中身を眺める。

**② `CLAUDE.md` とは何か（実物を見せる）**
- `/init` が作るのは **ただのテキストファイル（Markdown）**。作業フォルダの直下に置かれ、隠しファイルでもない。**フォルダを開けば普通に見える**。
- 中身を1枚のスライドで見せる。「このプロジェクトについて」＋「お願い」程度の、**読めば分かる文章**でよいと伝えるのが目的。特別な書式を覚える必要はない。
- **`/init` の実行を待つ間にこのスライドを話す**と、待ち時間が無駄にならない。可能なら参加者の実物（`techshare-demo/CLAUDE.md`）を画面共有で開いて見せる。
- 大事なのは、**このファイルは人間が手で書き足してよい**こと。「日本語で返答して」「このフォルダは触らないで」といったチーム固有のルールを追記していくのが実運用。
- 混在層には **「AIへの申し送りノート」** というたとえが一番通じる。

**③ 会話が長くなったときの2つ**
- `/clear`：**会話をリセット**して仕切り直す。別の作業に移るときは、続けるより**クリアした方が結果が良くなる**。
- `/compact`：これまでのやりとりを**要約して圧縮**し、文脈を保ったまま続ける。

**④ 困ったときの2つ**
- **Esc キー**：AIの動作を**途中で止める**。「違う方向に走り出した」と思ったら即座に押す。最重要キー。
- `/rewind`：**前の状態まで巻き戻す**。手戻りが怖くなくなる。

**⑤ 覚えておくと便利な3つ**
- `@` でファイル名を指定すると、**そのファイルを見てもらえる**（例：`@index.html を直して`）
- `/model`：使うモデルを切り替える
- `/help`：使えるコマンドの一覧を出す。**これだけ覚えれば残りは自分で探せる**

**見せるもの（1つ）**
- 2×2 のカード。「**最初に打つ：`/init`**」「**流れを切る：`/clear`**」「**止める：Esc**」「**戻す：`/rewind`**」。
  → 数を絞ることが目的。一覧表で20個並べない。

**ひとことスライド文言案**
> 「覚えるのは4つでいい。残りは `/help` が教えてくれる」

**補足メモ**：**コマンド紹介はカタログにしない**。「こういう場面で、これ」の形でしか記憶に残らない。時間が押したら ①`/init`・②`CLAUDE.md` と ④Esc に絞ってよい（`/init` は講座タイトルに含むので必須）。

## 付録：OS別コマンド対応表・GUIでのやり方

> **方針**：ターミナルに打ち込むのは実質 **`claude` の1回だけ**。それ以外はすべて GUI で代替できるようにする。手順スライドは「**ダブルクリック等のマウス操作を主、コマンドを従**」で書く。

| やりたいこと | Mac（ターミナル） | Windows（PowerShell） | GUIでのやり方（こちらを主に案内する） |
|---|---|---|---|
| フォルダを作る | `mkdir ~/Desktop/techshare-demo` | `mkdir ~\Desktop\techshare-demo` | デスクトップで右クリック →「新規フォルダ」／「新規作成」→「フォルダー」 |
| そのフォルダでターミナルを開く | `cd ~/Desktop/techshare-demo` | `cd ~\Desktop\techshare-demo` | **Mac**：`cd ` と打ってフォルダをドラッグ&ドロップ<br>**Windows**：フォルダのアドレスバーに `powershell` と入力（Win11 は右クリック →「ターミナルで開く」） |

### コマンド互換性の注意（当日ハマる箇所）

- **`mkdir -p` は使わない**。Mac / Linux では一般的だが、**Windows の `cmd.exe` では `-p` という名前のフォルダが作られてしまう**。`-p` を外しても目的は達成できるので、**最初から外して両OS同じ形に揃える**。
- **`cmd.exe`（コマンドプロンプト）は案内しない**。`~`（ホームディレクトリ）もスラッシュ区切りも使えず、手順が3系統に増える。**Windows は PowerShell / Windows Terminal に統一**する。
- **パス区切りが違う**：Mac は `/`、Windows は `\`。PowerShell は `/` も受け付けるが、参加者が混乱するので**手順スライドはOSごとに分けて書く**。
- **`open` は Mac 専用、`start` は Windows 専用**。取り違えが起きやすいので、**確認手順の主役はダブルクリック**にする。
- **`pwd` は PowerShell でも動く**（`Get-Location` の別名）。ここは共通で書いてよい数少ないコマンド。
- **Windows のデスクトップが OneDrive 配下にある場合がある**。その環境では `~\Desktop` が存在せず `cd` が失敗する。**GUIルート（アドレスバーに `powershell`）ならこの問題を踏まない**ため、迷ったら GUI を案内する。

### さらにターミナルを減らしたい場合（任意・要事前検証）

- **VS Code / Cursor を使う**：フォルダを開いて統合ターミナル（`Ctrl` + `` ` ``）から `claude` を起動する。**左のファイルツリーで生成物がその場で見える**ので、ループの「確認」ステップがやりやすくなる。すでに VS Code / Cursor を使っている参加者にはこちらを勧めてよい。
- **デスクトップアプリ / IDE拡張という選択肢もある**。ただし**プランモードのキー操作（`Shift + Tab` 2回）や `/init` の見え方がCLIと異なる可能性がある**。本企画書は**CLI（ターミナル）を主ルート**として組んでいるので、これを本編ルートに変える場合は**開催前に実機で全手順を通し直すこと**。

> **実装済み**：`decks/20260803_claude-code-basics.md`（全31枚）。書き出しは `build/` に HTML / PDF。**全スライドを PNG 書き出しで目視確認済み**（はみ出しなし）。以下は、そのときの判断と踏んだ落とし穴の記録。

- **ツール・運用**：この企画書と同じ basename（`20260803_claude-code-basics.md`）で `decks/` にデッキを作る。front matter は `theme: singularity`。デザインはテーマ側に集約されているので、デッキにインライン `<style>` は書かない。
- **テーマ側に3点追加した**（`themes/singularity.css`）。この講座はコマンドを大量に載せるため、既存テーマに不足していた分を補ったもの。**全デッキに効くので、既存デッキへの影響を再レンダリングで確認すること**（旧デッキはコードブロック未使用のため無影響を確認済み）。
  1. `code` / `pre` のスタイル（インライン＝薄グレー地に濃紺、ブロック＝濃紺地に白抜きのターミナル風）。テーマに定義がなく、default テーマの見た目のままだった。
  2. `dense` クラス（`pre` と引用を詰めて行数を稼ぐ）
  3. `section.src table` の font-size 明示（下記）
- **使うレイアウトクラス**（`<!-- _class: ... -->` で指定）：
  - 表紙 → `lead`
  - 基本ループの4ステップ、`Shift+Tab` の操作手順 → `flow`（連番ステップ図）
  - 「なぜ今きているのか（3つの理由）」、基本コマンドの2×2カード → `grid`
  - バイブコーディング vs 計画あり、「聞く」vs「作る」の対比 → `ba`（ビフォー/アフター表）
  - 締めの一言、「小さく回す」 → `center`
  - 付録・参考リンク → `refs`（または `src`）
  - ハンズオンの手順スライド、`CLAUDE.md` の実物サンプル → `dense`（`pre` と引用を詰めて行数を稼ぐ。この講座のために追加したクラス）
- **手順カードには `split` を付けない**。`split` は右側の青グラデパネルで本文幅を半分にするため、**手順が多いスライドでは確実にはみ出す**。Marp ははみ出しを警告しないので、**手順カードは必ず PNG 書き出しで見た目を確認する**。
- **Windows / Mac 2列の環境準備カード**は Markdown の表で組む（`ba` クラスの2列表を流用できる）。**セル内改行が必要**なので `<br>` を使う（`.vscode/settings.json` で `markdown.marp.html: true` 済み）。**3列以上にすると16:9で潰れる**ので、OS2列＋行見出しの構成を守る。ここは特に PNG での確認が必須。
- **コードブロック（`pre`）は「そのまま打ち込むコマンド」専用にする**。テーマの `pre` は濃紺地のターミナル風なので、**キー操作をここに入れると「打ち込むもの」と誤解される**。`Shift + Tab` を `pre` に入れて実際にそう見えたため、**引用（`>`）＋インラインコード＋「打ち込むのではなく、キーを押します」の明記**に変更した。
- **OS別のコマンドは、同じスライドに並べず「Mac」「Windows」の見出しを付けて上下に分ける**（横並びだとコピペ時に取り違える）。
- **日本語で太字が効かないパターンがある**：`**AIと"作る"**ための` のように、**閉じる `**` の直前が `"` や `」` で、直後が文字**だと太字にならず `**` がそのまま画面に出る。太字の範囲を語尾まで広げて `**AIと"作る"ための道具**` とすれば直る。閉じ `**` の直後が句読点（`。`『」』など）なら問題ない。**デッキを書いたら `grep -nE '["」』）]\*\*[^ 　]'` で洗い出す**。
- **付録のOS別コマンド対応表**は列が多いので `src` クラス（15px）単独で組む。`refs` と併用しない（font-size が衝突して 18px になり、はみ出す）。
- **発表者ノート**：各パートの「話すポイント」「ここで必ず言うこと」「補足メモ」を、各スライド末尾の `<!-- ... -->` コメントに入れる。特にハンズオンの**巡回チェックポイント**はノートに必ず残す。
- **コピペ用テキスト**：手順カードの指示文は、スライドに載せるだけでなく**当日チャットにも同じものを流す**前提。デッキとは別に、指示文だけを並べたテキストを付録として用意しておくと当日が楽になる。
- **図版の現状と、後追いで差し替えたいもの**：現在はすべて `flow` / `grid` / 表で表現している（raw HTML を使わない方針どおり）。差し替え候補は3つ。
  1. **「聞く」vs「作る」の対比**（PART 02）― 今は `ba` の2列表。「**コピペの矢印が消える**」絵にすると速い。
  2. **基本ループ / 進化版ループ**（PART 03・06）― 今は `flow` の横並び。本来は**円環図**にしたい（「回す」感が出る）。ただし PART 06 で同じ図に「計画・承認」を挿し込んで見せる構成なので、**2枚で同じ形式を保つ**ことを優先する。
  3. **`/init` → `CLAUDE.md` の生成図**（PART 08）― 今は `/init` のコードブロックと、次の1枚で `CLAUDE.md` の実物サンプルを見せる形にした。**実物を見せる方が図より伝わる**ので、差し替えの優先度は低い。
- **3枚目「今日つくるもの」は仮置き**。当日の完成形スクリーンショットに差し替える（発表者ノートに明記済み）。ローカル画像を貼っても `.marprc.yml` の `allowLocalFiles: true` があるのでフラグは不要。
