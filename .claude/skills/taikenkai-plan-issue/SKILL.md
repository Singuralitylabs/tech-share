# 体験会の企画 Issue を作る（→ tech-share-deck でデッキへ）

このリポジトリでは、体験会ごとに**企画 Issue を1つ作り、そこからスライド等のコンテンツを作る**。
企画 Issue は「企画書」で、次の工程（`tech-share-deck` スキル）がそのまま読んでデッキにする。だからこのスキルのゴールは、

- 体験会の前提（下記「0. 体験会の前提」）を満たした中身であること
- `tech-share-deck` と転記スクリプトが**機械的に読める形**であること（見出し・表の列・太字ラベル・「体験会名」欄）

の両方を満たす Issue を、ユーザーの確認を経て起票すること。ルールの正本はリポジトリの `CLAUDE.md` と `.github/ISSUE_TEMPLATE/presentation-plan.md`。食い違いに気づいたら CLAUDE.md を優先し、ユーザーに伝える。

スクリプトはこのスキルの `scripts/` にある。以下のコマンドは先にシェルで `SK=.claude/skills/taikenkai-plan-issue` を実行してから使う。

## 0. 体験会の前提（毎回これに合わせる）

ユーザーから毎回聞かなくてよい、決まっていること。Issue の中身はこれを満たすように組む。

- **対象**：プログラミング・AI開発に関心のある初心者、1回 20〜50 人。ターミナルを触ったことがない人もいる。
- **形式**：原則、月曜 20:00〜21:00 の 60 分、オンライン（Zoom）。月 2〜3 回。回によっては時間を長く取ることもある（そのときは手順 1 で聞いた想定時間で組む）。
- **時間配分**：約 15 分は定型スライド（冒頭：開始前の案内・SNS／末尾：アンケート・ご支援・今後のイベント・シンラボ紹介）で使う。**本編は想定時間から 15 分を引いた長さ**（60 分の回なら約 45 分）。
- **単発参加者が多い**：前回のおさらい・「前回までの流れ」・「前回のフォルダで」など、前の回を前提にした構成は入れない。必要な前提知識（例：CLAUDE.md とは）は、その回の本編の中で一言説明する。カリキュラム Issue（#12）に「前回までの流れを1枚置く」とあっても、こちらを優先する。
- **配布物**：何を配るか（サンプルコード・練習用データ・依頼文・救済用の完成形など）は Issue に書く。配り方（Zoom のチャットでファイル共有、リポジトリ、など）は回ごとに決めるので、決め打ちせずユーザーに確認するか、未定なら「配布方法：要確認」と書く。
- **作り方の紹介**：何かを作る・設定する回は、「AI に依頼する」「公式ツール（skill-creator など）」を中心に紹介し、手で書く方法は補足にする。
- **見るだけでOK**：有料プランやインストールが要る回でも、準備できていない人は見ているだけで参加できるようにする（事前案内とオープニングで伝える）。
- **ゴールの置き方**：完成品を作ることより、「わかった・自分でも打てた・違いを自分の目で見た」が残ることを優先する。ハンズオンの本体は時間が押しても削らない。
- **導線**：まとめの「次の一歩」でシンラボ（コミュニティ）での共有・相談につなげる。

## 1. 聞き取る

最低限ほしいのは次の3つ。会話や依頼文から分かるものは聞き直さない。

| 項目 | 例 | 分からないとき |
|---|---|---|
| 発表日 | 2026-11-16 | 必ず聞く（ファイル名・タイトルになる） |
| 想定時間 | 60分（原則）／90分 | 言われなければ 60 分で組み、長くする回かどうかを確認事項に入れる |
| テーマ／やりたいこと | 「GAS でフォームの自動返信」 | 必ず聞く |
| 体験会名（シリーズ） | AI駆動開発 / Web技術 / 業務効率化 | テーマから推測できれば候補を示して確認する |

あると精度が上がるもの（無ければ前提どおりに組み、最後の報告で「仮に置いた」と伝える）：形式（ハンズオン／座学）、参加者に必要な準備（有料プラン・インストール）、講師が見せる環境、題材にしたい具体例、外したい話題。

質問は一度にまとめて聞く。答えを待つ間にできる下調べ（手順 2）は先に進めておく。

## 2. 下調べ

起票前に GitHub MCP（`list_issues` / `issue_read`）で次を見る。gh が使えるなら `gh api repos/Singuralitylabs/tech-share/issues/N -q .body` でもよい。

1. **重複がないか**：`list_issues` を `labels: ["企画"]` で絞り、同じ発表日・同じテーマの Issue が無いか。あればユーザーに伝え、新規に作るか既存を育てるかを確認する。
2. **カリキュラム**：AI駆動開発シリーズなら #12（`[カリキュラム] AI駆動開発講座`）の該当月の「ねらい・座学で扱うこと・ハンズオン」を下敷きにする。ただし手順 0 の前提（おさらい無し・定型 15 分を除いた本編の長さ）が優先。
3. **同じシリーズの過去の企画**：直近の `体験会` ラベル付き企画 Issue（例：#18）を1〜2件開き、書きぶりと粒度をそろえる。同じ話題を前回と重ねすぎない（ただし前回を前提にもしない）。
4. **事実の確認**：コマンド名・設定項目・料金・バージョンなど変わりやすい事実は、公式ドキュメントで確かめて URL を「補足メモ」に書く。確かめられないものは書き切らず、「削ってよい / 注意する要素」の **要確認** に回す（デッキがそのまま出典になってしまうため、もっともらしい値を足さない）。

## 3. 構成を組む

[references/issue-skeleton.md](references/issue-skeleton.md) の骨組みに沿って組む。

- **時間**：オープニング 2 分＋本編のパート＋応用・まとめ＋定型 15 分 ＝ **想定時間**（原則 60 分）。ハンズオンのある回は、60 分の回でハンズオンに 20 分前後を確保する（初心者は必ず詰まる人が出る）。時間を長く取る回は、増えた分をまずハンズオンと質疑に回す。
- **枚数**：座学は 1 スライド＝約 1 分。ハンズオンは「出しっぱなしにする手順スライド」を 1 枚と数える。60 分の回なら本編はおおむね 15〜20 枚＋表紙（長く取る回は座学の時間に合わせて増やす）。
- **パートの型**：Before（AI に何もせず頼む・毎回説明する）→ After（〇〇すると変わる）を自分の目で比べられる形が、この体験会では一番伝わる。「覚えて帰る1つ」をこの比較にする。
- **ひとことスライド文言案**：デッキの `##` 見出しにそのまま使われる。体験会デッキの本編（`tkb`）は見出しが 44px と大きいので、**全角 24 字分以内**（半角は 0.5 字）の一文にする。
- **スライド構成表**：各スライドの中身に、使うレイアウトクラスを「②置き場所（`tkb grid`）」のように添える。体験会デッキは表紙 `lead tkt`、本編はすべて `tkb ＋ レイアウトクラス`。`tkb` は文字が大きく、1 枚に入るのは要点 3〜4 個まで。`trend` / `pair` / `split` / `refs` は `tkb` と併用できないので本編には書かない（`src` は参考スライドだけ）。クラスごとの入る量は `.claude/skills/tech-share-deck/references/layouts.md` の「tkb」節。
- **ハンズオン**：依頼文・コマンド・サンプルデータは**全文を Issue に書く**（配布ファイルと当日のチャット貼り付けの元になる）。「うまく動かないとき」と救済策（完成形を貼れば追いつける）を必ず入れる。
- **事前案内・配布物**：参加者に配るファイル、救済用ファイル、講師が用意するもの（デモ用ファイル・チャット貼り付け文・期待する出力の控え）を列挙し、配布方法（その回で決めたもの。未定なら要確認）を書く。

## 4. 本文を書いてチェックする

本文をスクラッチパッド（リポジトリの外）に Markdown で書き、チェックをかける：

```bash
python3 $SK/scripts/check_plan.py <下書き.md>
```

- `ERROR` は全部直す：必須の見出しの欠落、「体験会名」欄が空・記入例のまま（デッキ転記の `taikenkai_slides.py wrap` がここを読むので、空だと転記が止まる）、発表日の形式、各パートの「話すポイント」「ひとことスライド文言案」の欠落、骨組みの `〈〉` の残り。
- `WARN` は候補：月曜以外・過去の発表日、タイムテーブルの合計が「想定時間」欄と合わない、定型 15 分の行が無い、見出しが長い、スライド構成の枚数が合わない、`tkb` と併用できないクラス、前回前提の構成に見える行。意図したものなら残してよい（最後の報告で伝える）。

タイトルは `[企画] <タイトル案>（YYYY-MM-DD・ハンズオン60分）` の形にする（座学なら `座学60分`、時間を長く取る回は `ハンズオン90分` のように想定時間に合わせる）。

## 5. 確認して起票する（外部に出る操作）

Issue の作成は共有の場への書き込みなので、**下書きをユーザーに見せて了承を得てから**作る（ユーザーが「Issue を作って」と明示していれば、それが了承。ただし推測で埋めた箇所は起票前に一覧で伝える）。

- GitHub MCP の `issue_write`（`method: "create"`）で、`owner: Singuralitylabs`、`repo: tech-share`、`labels: ["企画", "体験会"]`、`assignees` に依頼者の GitHub ログイン。gh なら `gh api repos/Singuralitylabs/tech-share/issues -f title=... -F body=@下書き.md -f 'labels[]=企画' -f 'labels[]=体験会'`。
- 本文の末尾に、ツールの規定どおりの生成元フッターを付ける。
- 作成後に `issue_read` で読み直し、ラベル 2 つが付いていること、表が崩れていないことを確かめる。

カリキュラム Issue（#12）の表に新しい企画 Issue をリンクする場合も、#12 の編集は別の書き込みなので、内容を示して了承を得てから行う。

## 6. 報告して次の工程へつなぐ

最後に短く伝える：

- 作った Issue の URL とタイトル、発表日、体験会名
- 推測で置いた箇所（形式・準備物・題材など）と、**要確認** の一覧
- check_plan.py の WARN を残した箇所とその理由
- 次の一歩：内容が固まったら「Issue #N からデッキを作って」で `tech-share-deck` スキルがデッキ（`decks/YYYYMMDD_<topic>.md`）を作る。配布ファイルの準備も Issue の「事前案内・配布物」から起こせる。

起票後の修正（コメントでの議論を本文に反映するなど）は、**本文が正、コメントは経緯**の運用に合わせ、合意した内容を本文に書き戻す。
