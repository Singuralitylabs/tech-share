# Tech Share デッキ作成（企画 Issue → Marp）

企画 Issue に書かれた構成を、リポジトリ共通の見た目と運用ルールを満たす Marp デッキに起こす。
ルールの正本はリポジトリの `CLAUDE.md`。このスキルはそれを「迷わず・漏れなく」実行するための手順と道具をまとめたもの。
食い違いに気づいたら CLAUDE.md を優先し、ユーザーに伝える。

このデッキは発表のあと何度も見返され、Issue は後から編集できて git 履歴に残らない。だから**デッキ単体で企画の中身が分かる**（発表者ノートに話すポイントが全部ある）ことが、見た目と同じくらい大事。

## 0. 前提

- 作業ディレクトリはリポジトリ直下（`.marprc.yml` を読ませるため）。
- PNG 書き出しの前に `export CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"`。
- スクリプトはこのスキルの `scripts/` にある。以下のコマンドは先にシェルで `SK=.claude/skills/tech-share-deck` を実行してから使う。

## 1. 企画 Issue を読む

- 番号が分かっていれば GitHub MCP の `issue_read`（`method: "get"`、議論は `get_comments`）か `gh issue view N --json title,body,labels,comments`。分からなければ `list_issues` を `labels: ["企画"]` で絞り、どれか確認する。
- **本文が正、コメントは経緯**。食い違ったら本文に従う（コメントで合意した変更が本文に未反映なら、ユーザーに確認）。
- **ラベルを必ず見る**。`体験会` が付いていれば、表紙と本編のクラスが変わり（手順 3「体験会デッキの表紙と本編」）、手順 4 が必須になる。
- 拾うもの：発表日（→ファイル名。体験会でないデッキは表紙の kicker にも）、体験会名（`体験会` ラベル時。「基本情報」表の「体験会名」欄 → 表紙の見出しと定型スライド）、タイトル案（体験会デッキでは表紙の `sub` に入る「その回のテーマ」）、形式・時間、狙い・通しのメッセージ、タイムテーブル、各パートの「話すポイント／見せる数字／ひとことスライド文言案／補足メモ」、「スライド構成」表（枚数と中身）、「Marp 実装メモ」（使うクラスや注意点の指定）、出典。

Issue が骨子として未完成（文言案や構成表が空）なら、勝手に埋めずに、何が足りないかをユーザーに伝えて進め方を相談する。
体験会でまだ企画 Issue が無い場合は、先に `taikenkai-plan-issue` スキルで企画 Issue を起票する（デッキが読む形の本文をそろえるため）。

## 2. スライドの割り付けを決める

書き始める前に、「スライド構成」表の行 → スライド1枚ずつ、の対応表を頭の中（長ければメモ）で作る。

- 枚数は構成表に合わせる。パートの「各スライドの中身」①②… が1枚ずつになる。
- 見出し（`##`）は「ひとことスライド文言案」をそのまま使う（「」は外す）。2枚目以降のスライドは、そのパートの話すポイントから同じトーンの一文を作る。
- 1枚1メッセージ、要点3〜4項目。入りきらない話は削らずに発表者ノートへ回す。
- レイアウトは [references/layouts.md](references/layouts.md) の「選び方の目安」で選ぶ。各クラスは Markdown の構造（`ul`/`ol`/表/`#`）に装飾が当たるので、書き方の形も同ファイルを見て合わせる。Issue の「Marp 実装メモ」にクラス指定があればそれが優先。
- 数字・固有名詞・日付は Issue に書いてあるものだけを使う。もっともらしい数値を足さない（事実確認は発表者の責任範囲で、デッキが出典になってしまうため）。出典が Issue にあれば `src` の APPENDIX スライドに起こす。
- Issue に無い事実（リリース月・価格など）が構成上どうしても要るときは、**スライドには出さず**、その項目を省くか一般的な言い方にとどめ、発表者ノートに `要確認：〇〇` と書く。スライドに仮の値を置くと、そのまま本番で読まれてしまう。

Issue の中で食い違いがあるとき（例：構成表の「合計20枚」と内訳の合計18枚）は、**より具体的な方（内訳・各パートの記述）に従い**、どちらを採ったかを最後の報告で明示する。本文とコメントの食い違いは手順 1 のとおり本文を正とする。どちらとも決められない食い違い（パートの有無、対象者の違いなど）は、デッキの方向が変わるのでユーザーに確認する。

## 3. デッキを書く

ファイル：`decks/YYYYMMDD_<topic>.md`（発表日。topic は英小文字とハイフン、既存例：`ai-trend`, `claude-code-basics`, `deploy-web`, `claude-md`）。

front matter（既存デッキと同じキーを揃える。スタイルは書かない）：

```yaml
---
marp: true
theme: singularity
size: 16:9
paginate: true
lang: ja
title: <タイトル>
description: <通しのメッセージを1〜2文で>
author: シンギュラリティ・ラボ
footer: '<タイトル（短め）> ｜ シンギュラリティ・ラボ'
---
```

構成の順番：

1. 表紙（`lead`。体験会デッキは `lead tkt`）— コメントの**1行目**に `企画 Issue：https://github.com/Singuralitylabs/tech-share/issues/N`、続けて狙い・通しのメッセージ・対象・前提。
2. `OVERVIEW`（ゴールと進め方／今日の流れ）— 構成表にあれば。
3. 本編 `PART 01` …（`<!-- _header: 'PART 0X · パート名' -->`）
4. まとめ（最後の PART か `CLOSING`）
5. `APPENDIX`（出典 `src`・注記 `refs split`）— 必要なら。`_footer: ''` を付ける。

### 体験会デッキ（`体験会` ラベル）の表紙と本編

体験会デッキは、前後に入る定型スライド（`tk`）と見た目をそろえるため、表紙と本編に専用クラスを使う。書き方の例と項目数の目安は [references/layouts.md](references/layouts.md) の「lead tkt」「tkb」節。

- **表紙は `lead tkt`**（前回の体験会資料と同じ中央寄せ）。見出しは `# <体験会名> 体験会` で固定、その回のテーマ（Issue のタイトル案）は `<p class="sub">…</p>`、団体名は `<p class="org">シンギュラリティ・ラボ</p>`。**日付の kicker は付けない**。体験会名は手順 4 の `wrap` が Issue の「体験会名」欄から入れるので、書く時点では `# 〇〇 体験会` でよい。
- **本編の各スライドに `tkb`** を付ける。`_class` は front matter の `class` と合成されないので、1枚ずつ `<!-- _class: tkb -->`・`<!-- _class: tkb grid -->` のようにレイアウトクラスと1行で併用する。OVERVIEW・CLOSING も本編に含む（表紙と定型スライドには付けない）。例外は APPENDIX の `src`・`refs split` で、`tkb` と併用すると崩れるので `tkb` を付けずにそのまま使う。
- `tkb` は文字が大きい（本文 37px）ので、通常デッキより入る量が少ない。grid は4枚なら説明2行まで、flow は4ステップまで、ba は表4行＋補足1個まで、dense はコードブロック3個まで、が目安。
- `tkb` と `trend`・`pair`・`split`・`refs`・`src` は併用できない（レイアウトが崩れる）。推移は `tkb flow` か `tkb ba` で表し、QR や図は本文の下に画像だけの段落（`![w:220](...)`）で置く（右に並べる `pair` 型は使えない）。

**発表者ノート**：各スライドの末尾に `<!-- ... -->` を置き、そのパートの「話すポイント」「見せる数字/エピソード」「補足メモ」を**省略せずに**落とす。目安時間（例：`2分。`）、口頭で添えること、聞かれたら答えることもここ。Issue を開かなくても発表できる状態がゴール。

書くときに踏みやすい落とし穴（どれも Marp は警告しない）：

- 閉じ `**` の直前が `"`・`」` などで直後が文字だと太字が効かない（`**AIと"作る"**ための` は失敗）。太字の範囲を語尾まで広げる。
- `_class` を2行書くと先の行が消える。`<!-- _class: refs split -->` のように1行で。
- `refs` と `src` は併用しない。出典は `src` 単独。
- `split` は本文幅が半分になる。項目が多いスライドには付けない。
- `pre`（コードブロック）は打ち込むコマンド専用。キー操作は引用＋インラインコード。
- インライン `<style>` は書かない（デザインは `themes/singularity.css` の担当）。

## 4. 体験会デッキ（`体験会` ラベル）の定型スライド

`templates/taikenkai-opening.md` を表紙の直前、`templates/taikenkai-closing.md` をデッキの最後（APPENDIX も含めた全スライドの後）に、全枚・順序どおり・文言そのままで入れる。手で写すと継ぎ目の `---` 漏れや1文字の改変が起きやすいので、スクリプトで入れる：

```bash
python3 $SK/scripts/taikenkai_slides.py wrap decks/YYYYMMDD_<topic>.md
```

アンケート・ご支援スライドの見出しと導入文にある体験会名（テンプレートでは「AI駆動開発」）と、表紙（`lead tkt`）の見出し `# <体験会名> 体験会` は、**企画 Issue 本文「基本情報」表の「体験会名」欄**から自動で同じ名前が入る。スクリプトは表紙コメントの企画 Issue URL から番号を読み、`gh issue view` で本文を取る（手順 3 で表紙を書いてから実行する）。

- gh が使えない環境（クラウドのセッションなど）では、手順 1 で `issue_read` した本文をスクラッチパッドにファイルで保存し、`--issue-file <そのファイル>` を付ける。
- 「体験会名」欄が空欄・記入例のままだとエラーで止まる（既定名のまま別の回に出るのを防ぐため）。Issue への記入をユーザーに頼むか、了承を得て値を `--event <体験会名>` で直接渡す。

（front matter と転記ガイドのコメントは除外され、継ぎ目の `---` とスライドごとの `_paginate: skip` / `_footer: ''` もそのまま入る。）

その後、**差し替え欄**を最新化する。ここが定型スライドで文言を変えてよい唯一の箇所で、見出しと箇条書きの型は残す：

1. 「今後のイベントのお知らせ」— 小見出し（シリーズ名）と開催日程（3〜4件が目安）
2. 「○月の主なシンラボ活動の紹介」— 見出しの月と箇条書き
3. 体験会名（Issue の「体験会名」欄から入ったもの）— 表紙と、opening・closing のアンケート・ご支援スライド全部（スライド間も）で同じ名前になっていること。Issue 側の欄を後から直したら、デッキも合わせる（`wrap` は転記済みのデッキには何もしないので、手で直す）

定型スライドの `_class` にある `tk`（体験会専用クラス）や、「最後に」の後の空白の青スライド・付録「Sinlab Knowledge」はテンプレートどおりに残す（前回の体験会資料に合わせた構成）。

最新の日程・活動は Issue にもリポジトリにも無いことが多い。分からなければ推測で書かず、ユーザーに聞く（すぐ分からない場合はテンプレートのまま残し、最後の報告で「差し替え欄が未更新」と明示する）。

## 5. 規約チェック

```bash
python3 $SK/scripts/check_deck.py decks/YYYYMMDD_<topic>.md [--taikenkai] [--issue-file <Issue 本文>]
```

体験会デッキでは、表紙と定型スライドの体験会名を企画 Issue の「体験会名」欄と照合する（gh で取得。gh が無ければ `--issue-file` で本文を渡す。どちらも無いと WARN で照合を飛ばす）。`--taikenkai` を付けると、表紙が `lead tkt` でない・本編に `tkb` が無い・`tkb` と併用できないクラスがある・`tkb` で項目が多すぎる、も WARN で出る。

- `ERROR` は全部直す（front matter、表紙の Issue URL、`_class` 重複、定型スライドの欠落・改変・合体など）。
- `WARN` は候補。太字崩れ・ノート欠落・`split` の項目数などを見て、直すか判断する。差し替え欄がテンプレートのままという WARN は、ユーザーに確認済みなら残してよい。

## 6. PNG で全スライドを目視確認

はみ出し（下が切れる）はスクリプトでも Marp でも検出できないので、画像で見るしかない。

```bash
export CHROME_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
npx @marp-team/marp-cli --no-stdin --images png decks/YYYYMMDD_<topic>.md -o <scratchpad>/slide.png </dev/null
```

- `--no-stdin` と `</dev/null` が無いと標準入力待ちで止まる。出力先はスクラッチパッド（リポジトリに置かない）。
- 生成された `slide.001.png` … を**全部** Read し、はみ出し・合体したスライド・`**` の露出・空のカード・崩れたレイアウトを探す。定型スライドも見る（継ぎ目の合体はここで分かる）。
- 直したら該当デッキを再書き出しして確認し直す。はみ出しは、項目を減らしてノートへ回す／スライドを分ける／`split` を外す、の順で対処する。

## 7. 紐付けと仕上げ（外部に出る操作は確認してから）

- Issue 本文の「デッキ」欄にデッキのパスを書き戻す — Issue の編集は共有の場への書き込みなので、内容を示してユーザーの了承を得てから行う。
- コミットするなら本文に `Closes #N`。コミット・プッシュはユーザーに頼まれたときだけ。プッシュは毎回、送り先を示して承認を得る。

## 8. 報告

最後に短く伝える：作ったファイル、枚数（本編／定型）、使ったレイアウトの内訳（体験会デッキなら表紙 `lead tkt`・本編 `tkb` になっているか）、Issue から意図的に変えた点（あれば理由）、Issue 内の食い違いをどちらで採ったか、ノートに書いた `要確認` の一覧、残っている確認事項（差し替え欄・数値の鮮度・WARN を残した箇所など）。
